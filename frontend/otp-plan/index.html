4.4  /  Generate & Penyimpanan OTP

  • Gunakan CSPRNG — mis. crypto.randomInt, secrets.randbelow, SecureRandom. Jangan Math.random() / rand().
  • Kode 6 digit dengan leading zero dipertahankan ("004821").
  • Simpan hash, bukan plaintext: HMAC_SHA256(pepper, otpId + ":" + code).
  • OTP_PEPPER disimpan di secret manager / env — bukan di database.
  • Satu OTP aktif per (user, purpose): saat resend, OTP lama di-set invalidated_at.
  • OTP bersifat single-use: setelah valid langsung consumed_at.

Prinsip penyimpanan

Kode plaintext tidak pernah menyentuh disk, log, maupun respons API.

Yang tersimpan hanyalah hash 64 karakter. Kode asli hanya hidup di memori saat pembuatan dan di dalam payload job pengiriman.

Algoritma

HMAC-SHA256

Perbandingan

timing-safe

4.5  /  Logika Verifikasi (pseudocode)

verifyOtpPseudocode
verifyOtp(userId, code):
  BEGIN TRANSACTION
    user = users.findById(userId) FOR UPDATE
    if user.status == ACTIVE          -> throw USER_ALREADY_VERIFIED

    otp = otpCodes.findLatestActive(userId, 'REGISTER')   -- belum consumed & belum invalidated
    if otp == null                    -> throw OTP_EXPIRED
    if otp.expiresAt < now()          -> throw OTP_EXPIRED
    if otp.attempts >= otp.maxAttempts -> throw OTP_MAX_ATTEMPTS

    otp.attempts += 1                 -- naikkan SEBELUM membandingkan
    save(otp)

    if !timingSafeEqual(hmac(otp.id, code), otp.codeHash)
      -> throw OTP_INVALID(remaining = otp.maxAttempts - otp.attempts)

    otp.consumedAt  = now()
    user.status     = ACTIVE
    user.verifiedAt = now()
    save(otp, user)
  COMMIT

  return issueTokens(user)

Poin penting

Transaksi + row lock untuk mencegah race condition — dua request paralel dengan kode benar/salah tidak boleh dua-duanya lolos.

Konsekuensi

Pada concurrency test, hanya satu request verify yang boleh sukses; sisanya menerima USER_ALREADY_VERIFIED atau OTP_EXPIRED.

4.6  /  Logika Resend (pseudocode)

resendOtpPseudocode
resendOtp(userId, ip):
  user = users.findById(userId)
  if user.status == ACTIVE -> throw USER_ALREADY_VERIFIED

  if redis.exists("otp:cooldown:" + userId)  -> throw OTP_RESEND_COOLDOWN(retryAfter)
  rateLimit.check("otp:dest:" + destination, max=5,  window=1h)  -> OTP_RATE_LIMITED
  rateLimit.check("otp:ip:"   + ip,          max=10, window=1h)  -> OTP_RATE_LIMITED

  otpCodes.invalidateActive(userId, 'REGISTER')
  otp = createOtp(user)
  redis.set("otp:cooldown:" + userId, 1, ttl=60)
  queue.enqueue(SendOtpJob(otp.id, plainCode))   -- plainCode hanya ada di memori/job, tidak di DB

05

Keamanan

Checklist wajib. Seluruh item harus terpenuhi sebelum fitur dinyatakan selesai.

Kriptografi & penyimpanan

  • OTP dibuat dengan CSPRNG.
  • OTP disimpan sebagai HMAC hash + pepper.
  • Perbandingan kode memakai constant-time compare.
  • TTL pendek (5 menit) dan single-use.

Pembatasan & abuse

  • Batas percobaan verifikasi per OTP (5×), lalu OTP hangus dan user harus resend.
  • Cooldown resend 60 detik + batas per jam per tujuan dan per IP.
  • Rate limit endpoint register per IP.
  • Pertimbangkan CAPTCHA / device fingerprint di register untuk mencegah bot dan SMS pumping.

Eksposur & audit

  • Kode OTP tidak pernah muncul di respons API produksi maupun log — mask di logger.
  • Destinasi di-mask pada respons (b***@example.com, +62812****890).
  • HTTPS wajib; header keamanan standar aktif.
  • Audit log: otp_requested, otp_verified, otp_failed, otp_locked — tanpa menyimpan kode.

Lingkungan dev

Mode dev/staging boleh memakai kode tetap atau menampilkan OTP di log — dikontrol env flag dan nonaktif di produksi.

Observability & Operasional

Metrics, alert, dan cleanup job harian.

Metrics

  • Jumlah OTP terkirim
  • Success rate verifikasi
  • Rasio OTP_INVALID / OTP_EXPIRED
  • Latency & error rate provider
  • Jumlah kena rate limit

Alert

  • Lonjakan permintaan OTP dari satu IP / prefix nomor — indikasi abuse.
  • delivery failure melebihi ambang batas.

Cleanup job — harian

  • Hapus otp_codes dengan expires_at < now − 24 jam.
  • Hapus user PENDING_VERIFICATION yang lebih tua dari UNVERIFIED_USER_TTL_DAYS.
09

Rencana Testing

Empat lapis pengujian: unit, integration, concurrency, dan security.

Layer 01

Unit test

  • Generate OTP: panjang benar, hanya digit, leading zero aman.
  • Hash & verify: kode benar → lolos; kode salah → gagal.
  • Expiry: OTP kedaluwarsa ditolak (gunakan fake clock).
  • Attempts: percobaan ke-6 → OTP_MAX_ATTEMPTS.
  • Resend: OTP lama invalid setelah OTP baru dibuat.

Layer 02

Integration test

  • Register → verify → status ACTIVE dan token terbit.
  • Verify dengan kode salah berulang → terkunci, attempts tercatat.
  • Resend sebelum cooldown → 429; setelah cooldown → 200.
  • Verify OTP yang sudah consumed → ditolak (tidak bisa dipakai ulang).
  • Register ulang untuk akun PENDING_VERIFICATION → OTP baru terkirim.
  • Kegagalan provider → job retry, endpoint tetap merespons dengan benar.

Layer 03

Concurrency test

  • Dua request verify paralel dengan kode benar → hanya satu yang sukses.
  • Request resend paralel → hanya satu OTP aktif tersisa.

Layer 04

Security test

  • Brute-force 000000–999999 tidak mungkin selesai karena batas attempts.
  • OTP tidak muncul di log/response (grep pada log test).
